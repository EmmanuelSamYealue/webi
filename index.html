Module 1: Web Fundamentals & Architecture

Definition — Web Design: The planning and creation of the visual appearance, structure, content, and user experience of a website. It answers the question: What will the site look like, and how will people use it?

Definition — Web Development: The process of turning a design into working pages and features using code (HTML, CSS, JavaScript, and server-side languages). It answers the question: How do we make it actually work?

Definition — Front-end: Everything that runs in the user's browser — structure, styling, and behaviour. Also called client-side.
Definition — Back-end: Everything that runs on the server — databases, authentication, business logic, and APIs. Also called server-side.
Definition — Full-stack: A developer who works competently on both the front-end and the back-end.

1.1 The Internet and the World Wide Web Are Not the Same Thing

  • The Internet is the global physical and logical network of interconnected computers — cables, routers, satellites, and the protocols (TCP/IP) that move data between them.
  • The World Wide Web is a service that runs on top of the Internet. It is a collection of documents (web pages) linked together by hyperlinks and delivered using HTTP/HTTPS.

Analogy: the Internet is the road network; the Web is the delivery service that uses those roads.

1.2 The Client–Server Model

Client–server model: A system architecture in which a client (usually a browser) requests a resource, and a server (a computer or program) responds with that resource or with an error message.

A web server is software (such as Nginx or Apache) that listens for HTTP requests on a specific port and returns files or generated content. A browser is client software (Chrome, Firefox, Safari, Edge) that requests, interprets, and displays resources.

1.3 What Happens When You Visit a Web Page

  1. URL entry. The user types a URL or clicks a link. The browser parses the URL into scheme (https), host (example.com), port (443), path (/about), query string (?id=5), and fragment (#team).
  2. DNS resolution. The browser asks a DNS resolver to translate the human-readable domain name into an IP address (e.g., 93.184.216.34). This happens through a hierarchy: root servers → top-level domain (TLD) servers → authoritative name servers.
  3. Connection. For HTTPS, the browser and server perform a TCP handshake followed by a TLS handshake, which negotiates encryption keys and verifies the server's certificate.
  4. HTTP request. The browser sends a request with a method (usually GET), a path, headers (Accept, Accept-Language, User-Agent, Cookie), and sometimes a body.
  5. HTTP response. The server replies with a status code (200 OK, 404 Not Found, 301 Moved Permanently, 500 Server Error), headers (Content-Type, Cache-Control), and the body (usually HTML).
  6. Sub-resource requests. As the browser parses the HTML, it discovers and requests linked CSS, JavaScript, images, and fonts.
  7. Rendering. The browser builds the DOM from HTML and the CSSOM from CSS, combines them into a render tree, computes layout (positions and sizes), paints pixels, and composites layers onto the screen.
  8. Interaction. JavaScript runs, event listeners respond to user actions, and further network requests may occur (e.g., via fetch()).

Separation of concerns: A design principle stating that structure (HTML), presentation (CSS), and behaviour (JavaScript) should be kept in separate files. Benefits: easier maintenance, reusable styles, better accessibility, faster caching, and easier teamwork.

1.6 Static vs Dynamic Websites

  • Static site: The server sends the same pre-written files to every visitor. Fast, cheap, and secure; ideal for portfolios, documentation, and small business sites. Built with plain HTML/CSS/JS or a static site generator.
  • Dynamic site: The server generates HTML per request using server-side code (PHP, Python, Node.js, C#) and a database. Enables user accounts, search, shopping carts, and personalised content — but requires more security, testing, and infrastructure.

1.7 Who Sets the Standards?

  • WHATWG maintains the living HTML standard.
  • W3C publishes CSS specifications, accessibility guidelines (WCAG), and validation services.
  • ECMA International (TC39) standardises JavaScript (ECMAScript).
  • IETF publishes the HTTP and TCP/IP standards.
Progressive enhancement: Build a working HTML core first, then layer CSS on top, then add JavaScript as an enhancement. If a script fails or is blocked, the page still functions. The opposite approach — building something that only works with JavaScript enabled — is called graceful degradation when deliberately planned.

1.8 Beginner's Corner — See the Client–Server Model for Yourself

Try this in five minutes

  1. Open any website in your browser (for example example.com).
  2. Press F12 (or right-click → Inspect) to open Developer Tools, then click the Network tab.
  3. Reload the page with F5. Watch the list fill up.

What you are seeing: every row is one request your browser (the client) sent, and the status column is the server's answer. The very first row is usually the HTML document; the rows after it are the CSS file, the JavaScript file, images, and fonts — the "request cascade" described in section 2.7.

Now try: click the first row and look at the Headers sub-tab. You will see the request method (GET), the request headers your browser sent, and the response headers the server returned — exactly the exchange described in section 1.3, steps 4 and 5.

Key idea: a web page is not one download. It is a conversation made of many small requests and responses.

Module 2: The Anatomy of a Website — HTML, CSS & JavaScript in Practice

Definition — Website anatomy: The set of files, folders, and connections that together make a website work. A website is not a single file; it is a folder of files that the browser requests one by one and assembles into a page.

2.1 The Three-Layer Cake of a Website

Every modern website is built from three layers, each with a distinct job:

Think of a human body.
HTML is the skeleton — it gives the page its structure: the head, the body, the arms (navigation), the legs (footer).
CSS is the skin, hair, and clothing — it gives the page its appearance: colours, fonts, spacing, layout.
JavaScript is the muscles and nervous system — it makes the page move: respond to clicks, validate forms, load new content.

Without HTML, there is nothing to display. Without CSS, the page is readable but plain. Without JavaScript, the page is static but still usable. That is the order of importance: content first, style second, behaviour third.

Why this structure matters

  • Organization: A visitor never sees your folders, but you and your teammates do. A messy root folder with 40 files is a maintenance nightmare.
  • Scalability: When the site grows to 50 pages, you add files to existing folders instead of creating chaos.
  • Collaboration: Another developer can open the project and immediately know where to find things.
  • Paths: The folder structure determines the URLs. css/style.css becomes https://example.com/css/style.css.
Rule: Use lowercase filenames and hyphens, never spaces. contact-form.html is fine; Contact Form.html becomes Contact%20Form.html in a URL and causes 404 errors on Linux servers (which are case-sensitive).

2.3 index.html — The Front Door

When a browser requests a folder (e.g., https://example.com/), the server looks for a default document. The convention is index.html (or index.php, index.js, default.html). If no index file exists, the server may show a directory listing or a 403 Forbidden error.

A minimal index.html looks like this:

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Home | My Portfolio</title>
    <link rel="stylesheet" href="css/style.css">
</head>
<body>
    <header>
        <h1>My Portfolio</h1>
        <nav>
            <ul>
                <li><a href="index.html">Home</a></li>
                <li><a href="about.html">About</a></li>
                <li><a href="contact.html">Contact</a></li>
            </ul>
        </nav>
    </header>
    <main>
        <h2>Welcome</h2>
        <p>This is the home page of my portfolio.</p>
    </main>
    <footer>
        <p>&copy; 2025 My Name</p>
    </footer>
    <script src="js/script.js" defer></script>
</body>
</html>

External stylesheet: A separate .css file linked from the HTML. The browser downloads it once and reuses it on every page — improving speed and maintainability. This is the recommended way to style a website.

2.5 The JavaScript File — The Brain

The JavaScript file (js/script.js) is linked near the end of the <body> with the defer attribute:

<script src="js/script.js" defer></script>

Inside script.js, you write the behaviour that responds to user actions:

// ---------- Wait until the page is ready ----------
document.addEventListener("DOMContentLoaded", () => {

    // ---------- Example: greet the user ----------
    const greetButton = document.querySelector("#greetButton");
    const output = document.querySelector("#output");

    if (greetButton && output) {
        greetButton.addEventListener("click", () => {
            output.textContent = "Hello! Welcome to my portfolio.";
        });
    }

    // ---------- Example: update the year in the footer ----------
    const yearSpan = document.querySelector("#year");
    if (yearSpan) {
        yearSpan.textContent = new Date().getFullYear();
    }

});

This file can do many things: validate forms, toggle menus, fetch data from a server, animate elements, and store data in localStorage. It is the layer that makes the page interactive.

2.7 How the Browser Loads Everything — The Request Cascade

  1. The browser requests index.html.
  2. It starts parsing the HTML and builds the DOM tree.
  3. When it encounters <link rel="stylesheet">, it requests css/style.css. CSS is render-blocking: the browser waits for it before painting, because rendering without styles would show a flash of unstyled content (FOUC).
  4. When it encounters <img>, it requests the image. Images are not render-blocking — the browser continues parsing and paints the image when it arrives.
  5. When it encounters <script src="..." defer>, it downloads the script in the background, then runs it after parsing is complete.
  6. The browser combines DOM and CSSOM into a render tree, calculates layout, paints pixels, and composites them on screen.
  7. JavaScript runs, attaches event listeners, and the page becomes interactive.
Why CSS goes in the <head> and JS often goes at the end with defer: CSS must be ready before the first paint to avoid a flash of unstyled content. JavaScript, on the other hand, often needs the DOM to exist before it runs, and blocking scripts delay rendering — so we load them with defer or place them just before </body>.

2.11 Key Takeaways

  • A website is a folder of files, not a single document.
  • index.html is the default entry point.
  • HTML provides structure, CSS provides presentation, JavaScript provides behaviour.

2.12 Beginner's Corner — Build the Three-File Site in Ten Minutes

Step by step

  1. On your computer, create a folder called my-website.
  2. Inside it, create two sub-folders: css and js.
  3. In the main folder, create a file called index.html and paste the code from section 2.8 (File 1).
  4. In the css folder, create style.css and paste File 2.
  5. In the js folder, create script.js and paste File 3.

Module 3: Web Pages, Websites, Web Applications, Software & Applications

Why this matters: These five words are often used interchangeably in everyday speech, but they describe different things. The difference affects how you design, test, secure, and describe a project — and it affects the career path you choose.

3.1 Web Page — A Single Document

Web page: A single HTML document delivered over HTTP or HTTPS and rendered by a browser. It has its own URL and its own content.
  • Example: https://example.com/about.html is a single web page.
  • Analogy: A single page in a book.
  • What it contains: text, images, links, forms, media — everything visible in the browser window.
  • Key trait: It is the atomic unit of the web. A website is made of web pages.

3.2 Website — A Collection of Related Pages

Website: A collection of related web pages, usually under a single domain name, connected by hyperlinks and sharing navigation, design, and purpose.
  • Example: https://www.bcu.edu.lr — the whole site: home page, about page, admissions page, contact page, and so on.
  • Analogy: A whole book, with chapters and an index.
  • Key traits: Shared header and footer, consistent navigation, one domain, one visual identity.
  • Primary purpose: Usually to present information to visitors — reading, browsing, learning.

3.3 Web Application — A Website That Behaves Like Software

Web application (web app): A web-based program that processes user input, manages state, and performs meaningful tasks — often with user accounts, data storage, and complex logic. It runs in a browser but behaves like a desktop program.
  • Examples: Gmail, Google Docs, Trello, online banking, Facebook, a to-do list app, an online shop's checkout.
  • Analogy: An interactive workbook or a tool — not just something to read, but something to use.
  • Key traits:
    • User accounts and authentication
    • Data persistence (saving, editing, deleting)
    • Complex interactions and state management
    • Often communicates with a server via APIs
    • May be a single-page application (SPA) that updates without reloading
  • Primary purpose: To do something with data — send an email, edit a document, manage a project, buy a product.

3.4 Software — The Broadest Term

Software: Any collection of instructions and data that tells a computer what to do. It is the umbrella term for everything that runs on a computer.
  • Includes: operating systems (Windows, macOS, Linux), drivers, desktop programs (MS Word, Photoshop), mobile apps, web apps, firmware, scripts, and utilities.
  • Analogy: Any published work — a book, a film, a piece of music, a tool. It is the broadest category.
  • Key point: Not all software is a web app. Not all software is an application. An operating system is software, but it is not typically called an "application".

3.5 Application (App) — Software for a Specific User Task

Application (app): A software program designed to help a user perform a specific task. Applications can be desktop, mobile, web-based, or command-line.
  • Examples: Microsoft Word (desktop), WhatsApp (mobile), Gmail (web), git (command-line).
  • Analogy: A specific tool in a toolbox — a hammer, a screwdriver, a saw.
  • Key point: An application is a subset of software. An operating system is software but not an application. A web app is an application that runs in a browser.

Module 4: The Evolution of the Web — Web 1.0, 2.0, 3.0 & Blockchain

Why learn the history? Understanding where the web came from helps you understand where it is going. It also lets you evaluate buzzwords like "Web3" and "blockchain" critically instead of accepting them blindly.

4.1 Web 1.0 — The Read-Only Web (1991 – ~2004)

Web 1.0: The first generation of the World Wide Web, characterized by static pages, one-way communication, and a small number of content publishers.

Characteristics

  • Static HTML pages: Content was written once and rarely changed. No databases, no user accounts.
  • One-way communication: Publishers created content; visitors only read it. There were no comments, likes, or shares.
  • "Brochureware": Most corporate sites were digital brochures — a home page, an "About Us" page, and a contact page.
  • Dial-up connections: Slow, expensive internet access. Pages had to be lightweight.
  • Navigation through directories: Early search engines like Yahoo were curated lists of links, not algorithmic search.
  • Limited interaction: Clicking links and filling in simple forms was the extent of it.

Examples

  • Early Yahoo directory (a hand-organised list of websites)
  • GeoCities personal home pages
  • Static corporate websites of the late 1990s
  • Early news sites that simply reproduced print articles

Limitations

  • No user participation — visitors could not contribute content.
  • No dynamic content — every visitor saw the same page.
  • No social features — no profiles, comments, or sharing.

4.2 Web 2.0 — The Read-Write Web (~2004 – Present)

Web 2.0: The second generation of the web, characterized by user-generated content, social interaction, platform-based services, and dynamic, interactive pages.

Characteristics

  • User-generated content: Anyone can create and share — social media posts, blog articles, wiki edits, video uploads, reviews.
  • Interactivity: Likes, comments, shares, ratings, follows, notifications.
  • AJAX: Pages update dynamically without a full reload (e.g., typing in a search box and seeing suggestions appear).
  • Platforms own the data: Facebook, Google, and Amazon host user content and control the infrastructure.
  • APIs and integrations: Services can talk to each other (e.g., "Log in with Google").
  • Cloud computing: Applications run on remote servers rather than local machines.
  • Mobile-first and responsive design: The web adapts to phones and tablets.

Examples

  • Facebook, Instagram, TikTok — social media platforms
  • YouTube — user-uploaded video
  • Wikipedia — collaborative editing
  • Twitter / X — real-time public conversation
  • Google Docs — collaborative document editing
  • Amazon reviews — user-generated ratings and feedback
  • Blogs and comment sections

Limitations

  • Centralized control: A few tech giants own the platforms and the data.
  • Privacy concerns: Data harvesting, targeted advertising, surveillance.
  • Misinformation: Content moderation is difficult and inconsistent.
  • Users do not own their data: If a platform bans you or shuts down, your content may be lost.

4.3 Web 3.0 — The Read-Write-Own Web (Emerging)

Web 3.0 (Web3): The emerging generation of the web, characterized by decentralization, blockchain technology, user ownership of data and digital assets, and machine-readable (semantic) data.

Characteristics

  • Decentralization: No single company or server controls the application. Data is spread across a network of computers.
  • Blockchain-based: Smart contracts, tokens, NFTs, and decentralized applications (dApps).
  • User ownership: Users own their data, identity, and digital assets — often through a crypto wallet.
  • Semantic web: Data is structured so machines can understand it, enabling smarter search and AI integration.
  • Permissionless innovation: Anyone can build on open protocols without asking a platform owner.
  • Trustless transactions: No intermediary (bank, platform, government) is required to verify a transaction.

Examples

  • Ethereum dApps: Decentralized applications that run on smart contracts.
  • Uniswap: A decentralized exchange (DeFi) where users trade tokens without a central exchange.
  • OpenSea: A marketplace for NFTs (digital collectibles and art).
  • IPFS (InterPlanetary File System): Decentralized file storage.
  • ENS (Ethereum Name Service): Human-readable names for crypto wallets (like DNS for blockchain).
  • Brave browser: Rewards users with crypto tokens for viewing privacy-respecting ads.

Challenges

  • Usability: Crypto wallets, seed phrases, and gas fees confuse beginners.
  • Scalability: Blockchains are slower and more expensive than centralized databases.
  • Energy consumption: Proof-of-Work blockchains (like Bitcoin) use enormous electricity.
  • Regulation: Legal status varies by country and is still evolving.
  • Hype and scams: Many "Web3" projects are speculative or fraudulent.
  • Not everything needs blockchain: Using a blockchain when a normal database would do adds cost and complexity for no benefit.

4.5 Blockchain — The Technology Behind Web3

Blockchain: A distributed, append-only digital ledger that records transactions across many computers in a way that makes past records nearly impossible to alter.

How it works (simplified)

  1. A transaction is requested. For example, "Send 1 coin from Alice to Bob."
  2. It is broadcast to a network of nodes. Thousands of computers around the world receive the request.
  3. Nodes validate it. Using consensus rules, they check that Alice actually has the coin and is allowed to send it.
  4. It is bundled into a block. Valid transactions are grouped together with a timestamp.
  5. The block is cryptographically linked to the previous block. Each block contains a hash (a digital fingerprint) of the block before it, forming a chain.
  6. The block is added to the chain and replicated. Every node updates its copy. Changing any past block would break every subsequent hash — so tampering is immediately detectable.

Key properties

PropertyMeaning
DecentralizationNo single authority controls the ledger; it is maintained by many nodes.
ImmutabilityOnce recorded, a transaction is extremely difficult to change.
TransparencyAnyone can inspect the ledger (though identities may be pseudonymous).
ConsensusNodes agree on the state of the ledger using rules such as Proof of Work or Proof of Stake.
ProgrammabilitySmart contracts can execute logic automatically when conditions are met.
The blockchain analogy: Imagine a shared Google Doc that everyone can read, nobody can secretly edit, and every change is permanently recorded with a timestamp. But instead of Google owning the document, thousands of computers each hold an identical copy, and they all agree on the contents through a mathematical voting process.

A simple smart contract example

// Pseudocode — a smart contract for a simple sale

    address seller;

4.7 Limitations and Critical Perspective

  • Not everything needs blockchain. If a normal database is faster, cheaper, and simpler, use it.
  • "Blockchain" is often a marketing buzzword. Many "blockchain" products are just ordinary databases with extra steps.
  • Environmental concerns: Proof-of-Work blockchains consume large amounts of electricity. Proof-of-Stake (used by Ethereum since 2022) is far more efficient.
  • Irreversibility is a double-edged sword: Good for security, bad for mistakes. If you send crypto to the wrong address, there is no "undo".
  • Regulatory uncertainty: Laws around crypto, NFTs, and DeFi vary widely and are still developing.
  • Scams and speculation: Rug pulls, pump-and-dump schemes, and fraudulent tokens are common.
When is blockchain a good fit? When multiple parties need to share data without trusting a central authority, when auditability is essential, and when the cost of tampering must be extremely high. It is a poor fit for high-speed, low-cost, private-data applications.

4.8 How This Affects You as a Web Designer / Developer

  • You will most likely build Web 2.0 sites and applications first — the core skills (HTML, CSS, JavaScript) remain the foundation.
  • Understanding Web3 lets you evaluate new tools, trends, and client requests critically.
  • Blockchain integrations (wallet connections, NFT displays, token payments) may become client requirements — knowing the concepts helps you ask the right questions.
  • The principles of accessibility, performance, and security apply to Web3 interfaces too — often more so, because mistakes can be irreversible.

4.9 Key Takeaways

  • Web 1.0 was read-only: static pages, one-way publishing.
  • Web 2.0 is read-write: user-generated content, social platforms, interactivity.
  • Web 3.0 aims to be read-write-own: decentralization, blockchain, user ownership.
  • Blockchain is a distributed, tamper-resistant ledger that enables cryptocurrency, smart contracts, NFTs, DeFi, and more.
  • Blockchain is powerful but not a universal solution — evaluate whether it fits the problem.
  • The core web technologies (HTML, CSS, JavaScript) remain essential in every generation.

Module 5: Introduction to HTML & Document Structure

HTML (HyperText Markup Language) is the standard markup language used to describe the structure and meaning of web content. It is not a programming language: it has no variables, loops, or logic. It consists of elements that label pieces of content so that browsers, search engines, and assistive technologies can understand them.

5.0 A Short History of HTML (1989 – Today)

HTML was not designed by a committee, and it was not designed all at once. It was invented by one person to solve one problem, and then it grew — messily — for three decades. Knowing this explains almost everything odd about modern HTML: why some tags are obsolete, why the language is forgiving of mistakes, and why there is no "HTML6".

The problem it was invented to solve

In 1980, Tim Berners-Lee, a physicist working at CERN (the European particle-physics laboratory near Geneva), was frustrated: thousands of researchers kept documents on incompatible systems, and finding a document meant asking a person. He wrote a small hypertext notebook program called ENQUIRE. Nine years later, in March 1989, he circulated a document titled "Information Management: A Proposal". His supervisor, Mike Sendall, scribbled on the cover: "Vague, but exciting." That proposal became the World Wide Web.

Definition — Markup language: A system for annotating a document so that parts of it can be distinguished — "this is a heading", "this is a paragraph", "this is a link". The annotations (tags) are separate from the text itself. HTML is a markup language, not a programming language: it has no variables, loops, or logic.

Definition — SGML: Standard Generalized Markup Language (ISO 8879, 1986). A huge, general-purpose metalanguage for defining markup languages. HTML was written as one application of SGML — which is why it uses angle brackets and opening/closing tag pairs. XML is a later, simplified subset of SGML; XHTML was HTML rewritten under XML rules.

The turning point: from appearance to meaning

In the 1990s, a page's structure and its look were tangled together:

<!-- How people wrote it in 1997 -->
<center><font face="Arial" size="5" color="navy"><b>Welcome</b></font></center>

<!-- How the same thing is written today -->
<h1>Welcome</h1>

In the first version, nothing says "this is the most important heading on the page" — it only says "make this text big, blue, bold, and centred". Change the design and you must edit every page. Break the connection and screen readers have no idea what the text is. The second version states the meaning; CSS decides how it looks. This shift is the single most important idea in the history of web design, and it is why Module 9 (Semantic HTML) exists.

Where did the semantic elements come from? Not from theory. Researchers analysed millions of real pages and noticed developers kept writing <div class="header">, <div class="nav">, <div id="footer">. HTML5 simply formalised the class names people were already inventing — <header>, <nav>, <footer>, <article>, <aside>. Good standards follow practice.

Why the history is worth knowing

  • It explains obsolete tags. <font>, <center>, <big>, <marquee>, and <blink> are not "wrong" — they are historical accidents that CSS made unnecessary. If you see them in an old tutorial, close the tab.
  • It explains why HTML is forgiving. XHTML failed because it demanded perfection; a single unclosed tag could blank a page. HTML5 instead defines, in detail, how to recover from errors. Forgiving is not the same as correct — validate your HTML anyway (Module 22).
  • It explains <!DOCTYPE html>. The short doctype replaced a monstrous line listing a DTD. It exists to switch browsers out of "quirks mode", a compatibility mode that imitates 1990s browser bugs.
  • It explains why tables are not for layout. Tables were the only reliable layout tool in the late 1990s. CSS Grid and Flexbox (Modules 12–13) ended that, which is why using tables for layout is now considered incorrect.
  • It explains who to trust. When an article says "HTML6 is coming" or "this tag is deprecated in HTML5.3", the author has misunderstood the Living Standard. Check MDN or the WHATWG specification instead.
Practical takeaway for a beginner: you do not need to learn any version number. Learn the current elements, learn semantics, learn CSS, and validate your work. Everything else in the history is context — useful context, but context.

5.3 Common Global Attributes

Global attributes may be used on almost any HTML element:

  • id — a unique identifier within the page; used by CSS (#name), JavaScript, and fragment links.
  • class — one or more space-separated reusable labels for styling and scripting.
  • style — inline CSS (avoid except for quick tests).
  • title — advisory extra information, often shown as a tooltip.
  • hidden — hides the element from rendering.
  • tabindex — controls keyboard focus order (use sparingly; prefer natural focus order).
  • lang — language of the element's content.
  • data-* — custom data attributes for JavaScript, e.g. data-user-id="42".

5.4 Comments and Whitespace

<!-- This is an HTML comment. It is not displayed. -->
<p>This is the first paragraph.</p>

HTML collapses runs of whitespace into a single space. Line breaks and indentation in your source code do not affect the rendered output — that is why <pre> and <br> exist. Never put passwords, API keys, or private remarks in comments; anyone can read the page source.

Important: Browsers are forgiving of malformed HTML and will try to "fix" it, but that repair is unpredictable and can break your layout or accessibility. Always write valid HTML and check it with the W3C validator.

5.5 Beginner's Corner — Your First Page, Line by Line

Reading the skeleton out loud

Beginners often copy the boilerplate without knowing what each line does. Read this aloud and it will stick:

  • <!DOCTYPE html> — "Browser, this is a modern HTML5 document."
  • <html lang="en"> — "Everything from here to the end is the document, and it is written in English."
  • <head> — "Here comes information about the page — the browser and search engines read it, but visitors do not see it."
  • <meta charset="UTF-8"> — "Use UTF-8 so accents and symbols display correctly."
  • <meta name="viewport" ...> — "On a phone, use the phone's real width instead of pretending to be a desktop."
  • <title> — "This is the name shown on the browser tab."
  • <link rel="stylesheet"> — "Fetch my stylesheet."
  • <body> — "Here is everything the visitor actually sees."

Exercise: Type the full skeleton by hand (do not copy-paste) into a new file called index.html, add one <h1> and one <p>, then open it in the browser. Change the <title> and reload — watch the browser tab change. That single change proves you understand the difference between <head> content and <body> content.

Module 6: HTML Text, Headings & Formatting

6.1 Headings

Heading elements (<h1> through <h6>) describe the title of a section and establish a document hierarchy. They are not a font-size tool. Screen readers and search engines use headings to build an outline of the page and to let users jump between sections.
  • Use exactly one <h1> per page, describing the page's main topic.
  • Do not skip levels — an <h3> should follow an <h2>, not an <h1>.
  • Headings should be descriptive ("Module 6: Text Elements"), not vague ("More").
  • Never choose a heading level because of its default size — control size with CSS.

6.2 Paragraphs and Block vs Inline Elements

<p> defines a paragraph — a self-contained block of prose.

Block-level element: Starts on a new line and takes up the full available width by default (e.g., p, div, h1, ul, section).
Inline element: Flows within a line of text and only occupies as much width as its content (e.g., span, a, strong, em, img).

A block element may contain inline elements and other block elements (with restrictions — a <p> cannot contain another <p>). An inline element must not contain a block element.

A nested list must be placed inside an <li>, never directly inside the parent <ul> or <ol>.

Navigation menus: A site menu is structurally a list of links. Wrapping it in <ul> gives screen-reader users an item count and lets CSS/JS treat it as a collection. Do not use lists for purely visual indentation.

Module 9: Semantic HTML & Page Structure

Semantic HTML: The practice of choosing HTML elements that describe the meaning and role of the content they contain, rather than generic containers. <nav> says "this is navigation"; <div class="nav"> says nothing at all.

9.1 Why Semantics Matter

  1. Accessibility: Screen readers and other assistive technologies announce landmarks ("navigation", "main content", "footer"), enabling fast keyboard navigation.
  2. SEO: Search engines use semantic markers to understand which parts of a page are primary content versus boilerplate.
  3. Maintainability: Readable code is easier for teammates (and your future self) to understand.
  4. Consistency: Built-in browser behaviour (e.g., <button> is focusable and keyboard-operable) comes for free.
  5. Future-proofing: Standards evolve; generic div soups do not gain new capabilities.

9.2 Layout (Landmark) Elements

<header>Introductory content for a page or a sectionUsually holds the site name, logo, and sometimes navigation. May appear more than once.
<nav>A major block of navigation linksReserve for primary menus and key link groups, not every set of links.
<main>The dominant, unique content of the pageOnly one per page; must not be inside header, footer, or nav.
<section>A thematic grouping of contentShould almost always begin with a heading. Not a generic wrapper.
<article>Self-contained content that could stand alone (blog post, news item, comment, card)Test: would it still make sense syndicated elsewhere?
<aside>Content tangentially related to the main contentSidebars, pull quotes, related links, advertisements.
<footer>Footer information for a page or sectionCopyright, contact details, secondary navigation.
<div>A generic block containerUse when there is no better semantic element — e.g., purely for styling hooks.
<span>A generic inline containerUse to style a portion of text.

9.4 The Document Outline

The nested sequence of headings forms an outline of the page, analogous to a table of contents. Correct nesting (h1 → h2 → h3, no skipped levels) lets assistive-technology users skim the document structure quickly. Think of the headings as a contract: if a user jumps to an <h2>, everything until the next <h2> should belong to it.

9.5 ARIA — When HTML Is Not Enough

ARIA (Accessible Rich Internet Applications) is a set of attributes that add accessibility information to elements that HTML cannot describe adequately — typically custom widgets such as tabs, sliders, and live regions.

<div role="alert" aria-live="polite">Your changes have been saved.</div>
<button aria-expanded="false" aria-controls="menu-panel">Menu</button>
First rule of ARIA: do not use ARIA if a native HTML element already provides the semantics. <button> is always better than <div role="button">, because the native element also gives you keyboard behaviour and focus management for free.

Module 10: Introduction to CSS, Cascade & Selectors

CSS (Cascading Style Sheets) is a stylesheet language used to describe the presentation of a document — its colours, typography, spacing, layout, and animation. CSS is written as a series of rules. Each rule has a selector (what to style) and a declaration block (how to style it), containing property–value pairs. 
/* selector  |      declaration block            */
h1          { color: #1a365d; font-size: 2rem; }
/* property      value                          */

10.1 Three Ways to Apply CSS

MethodSyntaxWhen to use
Inline<p style="color: navy;">Rarely. Highest specificity, cannot be reused, mixes content with presentation. Acceptable for email templates or quick debugging.
Internal<style> ... </style> in the <head>Single-page demos, critical above-the-fold CSS, or pages with unique one-off styling.
External<link rel="stylesheet" href="css/style.css">Recommended. One file styles the whole site; the browser caches it across pages, speeding up navigation.

10.2 The Cascade, Inheritance, and Specificity

When two rules conflict, CSS resolves the conflict using three ideas:

  1. Cascade (origin & order): Later rules override earlier rules of equal specificity. Author styles beat browser defaults; user stylesheets and !important change the order of precedence.
  2. Inheritance: Some properties (e.g., color, font-family, line-height) pass from parent to child automatically. Others (e.g., margin, border, padding) do not. Use the inherit, initial, and unset keywords to control this.
  3. Specificity: A weight assigned to a selector. The more specific selector wins.

Specificity weights

Selector typeWeightExample
Inline style1000style="..."
ID100#site-title
Class, attribute, pseudo-class10.notice, [type="text"], :hover
Element, pseudo-element1p, ::first-letter
Universal selector0*

Example: nav a:hover has specificity 0-0-1-2 (one pseudo-class + two elements) and beats a (0-0-0-1).

Avoid !important. It breaks the cascade and makes future maintenance difficult. If you need it, the underlying selector structure is usually wrong. Prefer low-specificity, single-class selectors (a convention often called BEM or "flat CSS").

10.6 Beginner's Corner — Reading a CSS Rule Out Loud

Anatomy of one rule

h1 { color: #1a365d; }

Say it like this: "For every h1 element on the page, set the color property to the value #1a365d."

  • h1 — the selector: who gets styled.
  • { } — the declaration block: the list of instructions.
  • color — the property: what is being changed.
  • #1a365d — the value: how it is changed.
  • ; — ends each declaration. Forgetting it is the single most common beginner CSS error, and it usually breaks only the declarations after the missing semicolon — which is why the error appears to come from the "wrong" line.

Exercise: in your browser, open DevTools → Elements, click any heading, and look at the Styles panel on the right. You will see every rule that applies to that element, in order of precedence, with overridden rules struck through. This panel is the fastest way to learn the cascade.

Colour and contrast

The WCAG contrast ratio compares the luminance of text and background, on a scale from 1:1 to 21:1.

  • 4.5:1 — minimum for normal-size body text (Level AA).
  • 3:1 — minimum for large text (18pt/24px, or 14pt bold) and for UI component boundaries and focus indicators.
  • 7:1 — Level AAA, recommended for maximum readability.
Never rely on colour alone to convey meaning. Error states must include text or an icon, not just a red border, because around 8% of men and 0.5% of women have some form of colour vision deficiency.

Module 12: The Box Model, Display & Positioning

12.1 The CSS Box Model

Box model: The rule that every element generates a rectangular box composed of four layers, from inside out: content → padding → border → margin. Understanding this model is essential because most layout bugs are box-model bugs.
LayerMeaning
ContentThe text, image, or child boxes. Sized by width and height.
PaddingTransparent space inside the border, between border and content. Increases the element's clickable area.
BorderThe visible edge. Has width, style, and colour.
MarginTransparent space outside the border, pushing other elements away.
* { box-sizing: border-box; }   /* width includes padding + border */

.card {
    width: 320px;              /* total width is now exactly 320px */
    padding: 20px;
    border: 1px solid #ccd5df;
    margin: 16px;
}

With the default content-box, a 320px-wide element with 20px padding and a 1px border actually occupies 362px. border-box removes that arithmetic, which is why it is applied globally in almost every modern project.

Margin collapsing

Vertical margins of adjacent block elements combine into a single margin equal to the larger of the two (not the sum). This also applies to a parent and its first/last child when no padding, border, or content separates them. Margin collapsing does not occur in flex or grid containers, nor with overflow other than visible.

Overflow

.scroll-area {
    max-height: 300px;
    overflow-y: auto;     /* visible | hidden | scroll | auto */
}

overflow: hidden clips content; auto adds scrollbars only when needed; a new block formatting context is created, which stops margin collapsing and clears floats.

12.4 z-index and Stacking Contexts

z-index controls which overlapping element appears on top, but only works on positioned elements (or flex/grid items). Elements are painted in stacking contexts; creating a new context (with position plus z-index, opacity < 1, transform, filter, and others) means a child's high z-index cannot escape its parent's context. Most "my modal is behind the header" bugs come from this.

12.5 Floats (Legacy)

Before Flexbox and Grid, float: left/right was used for layout. It is now reserved for its original purpose: wrapping text around images. Remember to clear floats with clear: both or a block formatting context so parents do not collapse.

Module 13: CSS Layouts — Flexbox & Grid

13.1 Flexbox (One-Dimensional Layout)

Flexbox (Flexible Box Layout): A layout model for distributing space among items along a single axis — either a row or a column. It excels at aligning items, sharing space, and adapting to unknown content sizes.

Key concepts: the main axis (direction set by flex-direction), the cross axis (perpendicular to it), and free space (what remains after item sizes are accounted for).

.navigation {
    display: flex;
    align-items: center;          /* cross-axis alignment */
    justify-content: space-between; /* main-axis distribution */
    gap: 1rem;
    flex-wrap: wrap;              /* allow items onto new lines */
}

Module 14: Responsive Web Design

Responsive Web Design (RWD): An approach in which a single HTML document adapts its layout and presentation to the size and capabilities of the device viewing it. The term was coined by Ethan Marcotte and rests on three pillars: fluid grids, flexible images, and media queries.

14.1 The Viewport Meta Tag

<meta name="viewport" content="width=device-width, initial-scale=1.0">

Without this tag, mobile browsers assume a desktop-width layout (about 980px) and zoom out, producing tiny, unreadable text. Setting width=device-width tells the browser to use the device's actual CSS width. Never disable zoom with user-scalable=no — it is an accessibility failure.

14.2 Mobile-First Design

Mobile-first means writing the base CSS for the smallest screen, then progressively adding complexity with min-width media queries. This produces simpler, faster CSS, forces prioritisation of content, and matches the majority of web traffic.

/* Base: single column (phones) */
.card-grid {
    display: grid;
    grid-template-columns: 1fr;
    gap: 1rem;
}

/* Tablet and up */
@media (min-width: 700px) {
    .card-grid { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

/* Desktop and up */
@media (min-width: 1000px) {
    .card-grid { grid-template-columns: repeat(3, minmax(0, 1fr)); }
}
Breakpoints should be content-driven, not device-driven. Resize the browser slowly and add a breakpoint at the width where the design starts to look cramped or awkward — not at a specific iPhone model's resolution.

14.3 Fluid Layouts and Flexible Media

img, video {
    max-width: 100%;
    height: auto;
}

.container {
    width: min(100% - 2rem, 1100px);
    margin-inline: auto;   /* horizontally centred */
}

h1 {
    font-size: clamp(1.75rem, 4vw, 2.75rem);  /* fluid type */
}
  • max-width: 100% prevents images from overflowing their container.
  • min(), max(), and clamp() let a value respond smoothly to the viewport without media queries.
  • margin-inline is the logical property equivalent of margin-left/right and adapts to right-to-left languages.

14.4 Responsive Images in Practice

<picture>
    <source srcset="hero.avif" type="image/avif">
    <source srcset="hero.webp" type="image/webp">
    <img src="hero.jpg" alt="Students collaborating in the computer laboratory">
</picture>

<picture> lets the browser pick the best format it supports, and (with media on <source>) lets you serve entirely different crops for portrait and landscape screens.

14.5 Container Queries

.card-container { container-type: inline-size; }

@container (min-width: 400px) {
    .card { display: flex; gap: 1rem; }
}

Media queries respond to the viewport; container queries respond to the size of the component's parent. This makes reusable components truly portable — a card can rearrange itself whether it sits in a wide main column or a narrow sidebar.

14.6 Testing Responsiveness

  • Use DevTools device emulation to check common widths (320, 375, 414, 768, 1024, 1440px).
  • Resize the window slowly and watch for overflow, overlapping text, and horizontal scrollbars.
  • Test with real content — long words, long names, and missing images reveal problems that dummy text hides.
  • Check touch targets: interactive elements should be at least 44×44 CSS pixels.

15.7 Beginner's Corner — A Tiny Form You Can Test Right Now

Watch the URL change

<form action="https://example.com/search" method="get">
    <label for="q">Search term</label>
    <input id="q" name="q" type="text">
    <button type="submit">Search</button>
</form>

Save this into a page, type web design in the box, and press Search. Look at the address bar: it becomes https://example.com/search?q=web+design.

What you just learned:

  • action is the address the form sends data to.
  • method="get" puts the data into the URL as ?name=value pairs — exactly the "query string" from Module 1. Spaces become + (or %20).
  • name="q" is the key; the text the user typed is the value.
  • Change method to post and the data vanishes from the URL. It is now in the request body — invisible to the user.
  • Delete the name attribute and submit again: the parameter disappears entirely. This is why "my form sends nothing" is almost always a missing name.

Try also: remove the <label> and click on the word "Search term". With the label present, clicking the text focuses the input; without it, nothing happens. That is a free usability and accessibility win.

Module 16: Form Validation & Web Security

16.1 Two Layers of Validation

Client-side validation runs in the browser before data is sent. It gives immediate feedback and reduces server load.
Server-side validation runs on the server after the data arrives. It is the only validation that can be trusted.

The reason is simple: the browser belongs to the user. Anyone can disable JavaScript, edit the HTML in DevTools, or send a raw HTTP request with curl or Postman that never touches your form at all. Client-side validation is a convenience; server-side validation is a requirement.

XSS — Cross-Site Scripting

XSS: An attack in which malicious JavaScript is injected into a page and executed in other users' browsers. It can steal session cookies, redirect users, modify page content, or perform actions on the victim's behalf.

17.12 Beginner's Corner — Your First Script, Explained

Four lines, one at a time

const button = document.querySelector("#greetButton");
const output = document.querySelector("#output");

button.addEventListener("click", () => {
    output.textContent = "Hello! Nice to meet you.";
});
  • Line 1: document is the whole page. .querySelector("#greetButton") means "find the first element whose id is greetButton". The result is stored in a constant called button.
  • Line 2: the same idea — find the element with id="output" and remember it as output.
  • Line 3: addEventListener("click", ...) means "from now on, when this element is clicked, run the code inside the braces". The code inside is a callback — a function you hand over to be run later.
  • Line 4: output.textContent = "..." replaces the text inside that element.

Why the order matters: if this script runs before the HTML exists, querySelector returns null and you get "Cannot read properties of null (reading 'addEventListener')". That is exactly why we add defer to the script tag, or wrap the code in document.addEventListener("DOMContentLoaded", ...).

Experiment: change textContent to innerHTML and set the value to "<strong>Hello</strong>". The word becomes bold — because innerHTML parses HTML. Now imagine a visitor typed that string into a comment box. That is XSS, and it is why textContent is the safe default.

Module 19: Web Accessibility (a11y)

Web accessibility is the practice of designing and building websites so that people with disabilities — visual, auditory, motor, cognitive, and neurological — can perceive, understand, navigate, and interact with them. "a11y" is a numeronym: a + 11 letters + y.

19.1 The POUR Principles (WCAG)

PrincipleMeaningExample requirements
PerceivableInformation must be presentable in ways users can perceive.Alt text, captions, sufficient contrast, not relying on colour alone.
OperableInterface components must be usable.Full keyboard access, visible focus, enough time, no seizure-inducing flashing.
UnderstandableContent and operation must be clear.Consistent navigation, clear labels, helpful error messages.
RobustContent must work with current and future user agents.Valid HTML, correct ARIA usage, meaningful names and roles.

WCAG has three conformance levels: A (minimum), AA (the common legal and practical target), and AAA (enhanced).

19.2 Practical Accessibility Checklist

  • Provide meaningful alt text for informative images; alt="" for decorative ones.
  • Associate every form control with a visible <label>.
  • Use semantic HTML and a logical, unbroken heading hierarchy.
  • Ensure everything works with the keyboard alone: Tab, Shift+Tab, Enter, Space, arrow keys.
  • Keep focus indicators visible — never write outline: none without providing a replacement.
  • Meet contrast ratios: 4.5:1 for body text, 3:1 for large text and UI boundaries.
  • Do not use colour alone to convey meaning — add text or icons.
  • Provide a "skip to main content" link as the first focusable element.
  • Ensure link text makes sense out of context ("View the timetable", not "click here").
  • Give every page a unique, descriptive <title>.
  • Provide captions and transcripts for audio and video.
  • Use ARIA only when native HTML cannot express the semantics.
  • Make sure interactive targets are at least 44×44 CSS pixels.
  • Avoid content that flashes more than three times per second.

19.4 Focus Management

  • Only one element has focus at a time; the browser tracks it in the tab order, which follows DOM order.
  • tabindex="0" makes an element focusable in normal order; tabindex="-1" makes it programmatically focusable but not tabbable; positive values reorder the tab sequence and should be avoided.
  • When content changes dynamically (a modal opens, an error appears), move focus deliberately so screen-reader users are not stranded.
  • :focus-visible lets you style focus only for keyboard users, so mouse clicks do not show a ring.

19.5 Testing Accessibility

  • Automated: Lighthouse, axe DevTools, WAVE — catch perhaps 30–40% of issues.
  • Keyboard-only: unplug the mouse and try to complete every task.
  • Screen reader: NVDA (Windows), VoiceOver (macOS/iOS), TalkBack (Android).
  • Zoom: test at 200% and 400% zoom, and with a 320px-wide viewport.
  • Colour: use a contrast checker and a colour-blindness simulator.

SEO is the practice of improving a website's visibility in organic (non-paid) search results. Search engines crawl pages, index their content, and rank them against queries using hundreds of signals. You influence those signals through content quality, technical structure, and page experience.

20.2 User Experience (UX) and Visual Design

User experience is the totality of a person's feelings and perceptions while using a product. Good UX reduces effort: users find what they need, understand what to do, and make fewer mistakes.
  • Consistency: keep spacing, typography, colours, and navigation patterns uniform across pages.
  • Visual hierarchy: size, weight, colour, and position should signal what matters most. Users scan in an F- or Z-shaped pattern.
  • Whitespace: generous negative space reduces clutter and improves comprehension.
  • Clear affordances: buttons should look clickable; links should look like links.
  • Feedback: every action should produce a visible response (hover states, loading indicators, confirmations).
  • Error prevention and recovery: prevent mistakes where possible; when they occur, explain them clearly and say how to fix them.
  • Design process: research → user flows → wireframe (grey-box structure) → visual mock-up → prototype → build → test → iterate.

20.3 Web Performance

Performance is a UX feature and a ranking factor. Slow sites lose users: every additional second of load time measurably reduces conversions.

22.3 Testing Checklist

  • Open every page; check for missing files (broken links and images).
  • Test forms with valid, missing, and malformed values; confirm error messages are clear.
  • Check layout at 320px, 375px, 768px, 1024px, and 1440px widths.
  • Inspect the Console and Network panels for errors and failed requests.
  • Navigate the whole site using only the keyboard.
  • Run an HTML validator (W3C Markup Validation Service) and a CSS validator.
  • Test with JavaScript disabled — is the core content still available?
  • Check text zoom at 200% without loss of content or functionality.
  • Proofread all text; check spelling and consistent terminology.

22.4 A Debugging Method

  1. Reproduce the issue consistently and note the exact steps.
  2. Read the error carefully — the message usually names the file, the line, and the type of problem.
  3. Locate the relevant HTML structure, CSS selector, or JavaScript value.
  4. Form a hypothesis about the cause before changing anything.
  5. Change one thing at a time and retest.
  6. Verify the fix and check for side effects elsewhere.
  7. Record the solution (commit message, README, or notes) so you do not repeat the investigation.
Common beginner bugs: a misspelled file path (case-sensitive on Linux servers but not on Windows); a missing closing tag; a CSS selector that does not match the HTML; querySelector running before the element exists; a form submitting and reloading the page because preventDefault() was forgotten; specificity conflicts solved by adding !important instead of fixing the selector.

Appendix D: How to Start — Where to Begin and in What Order

Purpose of this appendix: A beginner's question is almost never "what is a box model?" — it is "where do I actually start, and in what order?" This appendix answers that, step by step, and maps every step onto the modules in this book.

D.1 The short answer

Start with one page, in one folder, using three files — and build it this week. Not after you finish a course. Not after you understand everything. Now.

The order is fixed, and it is the same order the browser uses to load a page:

HTML first — give the page structure and meaning.
CSS second — make it look right.
JavaScript third — make it respond.

Skipping ahead (JavaScript before HTML, or a framework before CSS) is the single most common reason beginners quit. You cannot debug what you cannot read.

D.4 Your first 30 minutes

Do this now, in order

  1. Create a folder called my-website on your desktop.
  2. Open your text editor, create a new file, and type (do not copy) this:
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>My First Page</title>
</head>

    <h1>Hello, I am learning web design</h1>
    <p>This is my first paragraph.</p>

  1. Save it as index.html — inside the my-website folder. Make sure the editor is set to "All Files", not .txt.
  2. Double-click the file. It opens in your browser.
  3. Change the text inside <h1>, save, and press F5 in the browser. The page updates. You have edited a website.
  4. Change the text inside <title> and reload — the tab changes, the page does not. You have just learned the difference between <head> and <body>.
  5. Add <p>A second paragraph.</p> and reload. Notice it starts on a new line — that is a block element (Module 6).
  6. Press F12, click the Console tab, and type document.title. You have just talked to the DOM (Module 18).

That is the whole loop: write → save → reload → inspect. Everything from here is adding knowledge to that loop, not learning a new one.

D.5 The three traps

  1. Tutorial hell. Watching a fourth course feels productive and teaches almost nothing. The rule: for every hour of watching, spend two hours building something that was not in the tutorial.
  2. Starting with a framework. React, Vue, Bootstrap, and Tailwind all assume you already know HTML, CSS, and JavaScript. Learn the fundamentals first; frameworks then take days, not months. Bootstrap in particular hides the CSS you are trying to learn.
  3. Memorising instead of looking up. No professional remembers every CSS property. They remember that a property exists and where to find it. Keep MDN open in a permanent tab.
One more, specific to this subject: do not start with a website builder (Wix, Squarespace, WordPress themes) if your goal is to learn web design. They are excellent products, but they do the designing and the coding for you. Use them later, to ship a site quickly — not to learn how a site works.

D.8 How to use these notes

  • Read Modules 1–2 first. They explain what a website actually is — a folder of files that the browser assembles. Everything afterwards makes more sense.
  • Do every "Beginner's Corner" box. They are five-minute exercises, and they are where the learning happens. Reading about the box model is not the same as dragging its numbers in DevTools.
  • Follow the module order for the first pass, then jump freely. Modules 5–14 are the core; 15–19 are what turn a page into something professional; 20–22 are what make it shippable.
  • Build Appendix C (the Student Web Club) once you have finished Module 18. It is the smallest complete website in this book, and it uses almost everything.
  • Answer the review questions in Module 23 out loud. If you cannot explain a concept in plain words, you do not know it yet.

D.9 Milestone checklist

Tick these off. They are ordered, and each one is a real skill, not a topic you have merely read about.

  • ☐ I can create a valid index.html from a blank file, from memory.
  • ☐ I can link an external stylesheet and see the effect.
  • ☐ I can explain the difference between <head> and <body>.
  • ☐ I can style an element by class, and explain why a class beats an ID here.
  • ☐ I can centre a box horizontally and vertically without guessing.
  • ☐ I can lay out three cards in a row that stack on a phone.
  • ☐ I can build a form where every input has a label.
  • ☐ I can make a button do something with JavaScript.
  • ☐ I can find and fix a broken image path using the Network panel.
  • ☐ I can navigate my own site with only the Tab key.
  • ☐ I have published a page at a public URL.
  • ☐ I have committed my work to Git and can explain what a commit is.
The last word: web design is learned by making things and then fixing them. Your first page will be ugly. Your tenth will be better. The gap between them is not talent — it is the number of times you pressed F12 and asked "why is that happening?". Start today, start small, and finish something.
